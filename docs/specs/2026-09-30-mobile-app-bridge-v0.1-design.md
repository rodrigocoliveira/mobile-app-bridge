# `@rodrigocoliveira/mobile-app-bridge` v0.1 — Design

- **Date:** 2026-09-30
- **Status:** Approved in conversation, pending written-spec review
- **Scope:** Sub-project 1 of 3 of the "starterkit for a new brand" initiative (bridge → `mobile-app/` → `website/`)

## 1. Intent

Products are built once in the web app (Laravel + React/Inertia, or Vue in legacy products), and the mobile app is a thin Expo shell that loads it in a WebView. Some things only native code can do (camera permission, haptics, and later push, biometrics, local storage). The bridge lets the web page ask the native shell to do them **and await the answer**.

The design is deliberately a cleaned-up version of the bridge that ran in production in the Agendart app (`agendart-app/src/screens/AgendartWebview.js`). The mechanisms are unchanged: an injected `window` badge, `postMessage` from web to native, and `injectJavaScript` + `CustomEvent` from native to web. It adds one thing Agendart lacked, which is request/response correlation, so the web gets a `Promise`.

### Success criteria

1. The web side can `await bridge.call(method, params)` and get either the handler's result or a typed error.
2. The native side replaces a hand-written `<WebView>` + `onMessage` if/else with `<BridgeWebView handlers={...}>`, without losing any `WebView` prop or customization.
3. Every behavior in §7 is covered by an automated test. The flows in §8.2 are verified end to end on the iOS simulator using `example/`.
4. The package is published to npm as public, with CI and release automation mirroring `agno-frontend-sdk`.

### Non-goals for v0.1 (explicitly cut as over-engineering)

- Shared typed contracts (`defineContract`), capability lists / `supports()`, protocol version negotiation, server-side user-agent detection, a React hooks adapter, a Vue adapter.
- Built-in feature modules inside the package. Camera, haptics and "unsupported feature" handlers are **example code** in `example/` (and later in the starterkit's `mobile-app/`), not package code.
- Push, biometrics, secure storage, SQLite, media upload, IAP. Each is added later when a real product needs it.

## 3. Wire protocol

Every bridge message is JSON with the marker `"bridge": 1`. Messages without the marker are not bridge messages. The native side forwards them to the consumer's own `onMessage` (§5.2).

| Direction | Transport | Envelope |
|---|---|---|
| web → native (request) | `window.ReactNativeWebView.postMessage(string)` | `{ "bridge": 1, "kind": "req", "id": string, "method": string, "params"?: unknown }` |
| native → web (response) | `injectJavaScript` → `window.dispatchEvent(new CustomEvent('mobile-app-bridge', { detail }))` | `{ "bridge": 1, "kind": "res", "id": string, "ok": true, "result"?: unknown }` or `{ ..., "ok": false, "error": { "code": string, "message": string } }` |
| native → web (event) | same as response | `{ "bridge": 1, "kind": "evt", "name": string, "data"?: unknown }` |

Rules:

- Requests only flow web → native. Events only flow native → web.
- `id` is generated by the web side with `crypto.randomUUID()`. If that function is unavailable, a counter + timestamp is used instead.
- **Badge:** the native side injects the following before content loads (main frame only). Its presence is what makes `isApp` true.
  ```js
  window.__MOBILE_APP_BRIDGE__ = { platform: 'ios' | 'android', appVersion: string, buildNumber: string }
  ```

## 4. Web API (`/web`)

```ts
import { bridge, BridgeError } from '@rodrigocoliveira/mobile-app-bridge/web'

bridge.isApp: boolean                                   // getter: badge present AND window.ReactNativeWebView present
bridge.info: { platform, appVersion, buildNumber } | null
bridge.call<T = unknown>(method: string, params?: unknown, options?: { timeout?: number }): Promise<T>
bridge.on<T = unknown>(name: string, listener: (data: T) => void): () => void   // returns unsubscribe
```

- **SSR-safe:** importing the module never touches `window`. `isApp` and `info` are getters, and the `mobile-app-bridge` event listener is attached lazily on the first `call`/`on`. This matters for Inertia SSR.
- `timeout` defaults to `30_000` ms. `0` disables it.
- `BridgeError extends Error` has a `code: string`. The codes the package produces are listed below. A handler may also throw its own `code` (§5.1).

| Code | When |
|---|---|
| `NOT_IN_APP` | `call()` outside the app (rejects immediately, nothing sent) |
| `TIMEOUT` | no response within `timeout` |
| `UNKNOWN_METHOD` | the app build has no handler for `method` |
| `HANDLER_ERROR` | the handler threw without a `code` |

## 5. Native API (`/native`)

```tsx
import { BridgeWebView, useBridgeEmitter } from '@rodrigocoliveira/mobile-app-bridge/native'

const emitter = useBridgeEmitter()            // optional; only needed to send events
const webViewRef = useRef<WebView>(null)      // the normal react-native-webview ref

<BridgeWebView
  ref={webViewRef}
  emitter={emitter}
  source={{ uri: APP_URL }}
  trustedHosts={['app.brand.com', '*.brand.com']}     // load in the app AND may call handlers
  inAppHosts={['*.amazonaws.com', 'accounts.google.com']}  // load in the app, NO bridge access (optional)
  handlers={{
    'camera.requestPermission': async () => ({ granted: true }),
    'haptics.impact': async ({ style }) => { /* ... */ },
  }}
  {...anyOtherWebViewProp}
/>

emitter.emit('app.stateChange', { state: 'active' })
```

### 5.1 Handlers

- `handlers: Record<string, (params: any) => unknown | Promise<unknown>>`.
- If the handler resolves, the web receives `ok: true` with `result` set to the resolved value.
- If the handler throws, the web receives `ok: false` with `code: err.code ?? 'HANDLER_ERROR'` and `message: err.message`.
- If there is no handler for the method, the web receives `ok: false` with `code: 'UNKNOWN_METHOD'`.
- `handlers` may change between renders. The latest object is always used, and the WebView is not remounted.

### 5.2 Prop composition — the bridge never overrides a consumer prop

| Prop | Behavior |
|---|---|
| `onMessage` | Bridge messages (`"bridge": 1`) are consumed by the bridge. **Every other message is forwarded unchanged to the consumer's `onMessage`**. This lets legacy apps (Agendart `{ event_name }`) migrate one event at a time. |
| `onShouldStartLoadWithRequest` | The consumer's function runs first. If it returns `true` or `false`, that decision wins. If it returns `undefined`, the default policy (§6) applies. |
| `injectedJavaScriptBeforeContentLoaded` | The badge script runs first, then the consumer's script. |
| `injectedJavaScriptForMainFrameOnly` | Always forced to `true` (security, §6). It cannot be overridden. |
| `ref` | Forwarded to the underlying `WebView` unchanged (`reload`, `goBack`, `injectJavaScript`, …). |

### 5.3 Emitter

- `useBridgeEmitter()` returns a stable `{ emit(name, data?) }`.
- If `emit` is called before the page has finished loading, the event is queued. The queue is flushed on the page's first `onLoadEnd` and again after every reload. Example: the app is opened from a notification tap.
- **In-page buffering.** `onLoadEnd` does not guarantee that the page's code has already called `bridge.on(...)`. To cover the gap:
  - The badge script also installs `window.__MOBILE_APP_BRIDGE_BUFFER__`, which collects `evt` messages until the web client attaches and drains it.
  - The web client keeps any event that no listener was subscribed to for up to **10 seconds** (at most 50 events). It replays such an event to the first `on(name)` that subscribes within that window.
  - This makes a cold-start event such as "app opened from a push" reliable, and stale events expire on their own.
- An emitter not attached to any `BridgeWebView` keeps queuing. It does not throw.

### 5.4 Badge values

- `platform` comes from `Platform.OS`.
- `appVersion` comes from `Constants.expoConfig.version`.
- `buildNumber` comes from `Constants.expoConfig.ios.buildNumber` or `Constants.expoConfig.android.versionCode`.
- Any of these can be overridden through an optional `appInfo` prop.

## 6. Security and navigation policy

- **Host matching is exact on `URL.hostname`** (never substring). A `*.brand.com` entry matches subdomains of `brand.com` but not `brand.com` itself, and not `evilbrand.com`. This replaces Agendart's `indexOf` checks, e.g. `indexOf('aa')`.
- **Requests from untrusted origins are dropped.** `nativeEvent.url` is parsed, and if its hostname is not trusted, the message is ignored and no response is sent (a warning is logged in `__DEV__`).
- **What the policy does not affect.** `onShouldStartLoadWithRequest` only sees navigations. Scripts, `fetch`/XHR, images and styles (for example Google Analytics' `gtag.js`) load normally and never need listing. Agendart had to allowlist GTM, reCAPTCHA and Memed only because its policy sent every foreign navigation to the browser, including iframe loads on iOS.
- **Default navigation policy** applies when the consumer returns `undefined`:
  1. `http(s)` whose hostname is in `trustedHosts` or `inAppHosts`: load in the WebView. Only `trustedHosts` may call handlers. `inAppHosts` covers third-party pages that must stay inside the app, such as file previews, OAuth or 3-D Secure, without granting them the bridge.
  2. `http(s)` in a subframe (`isTopFrame === false`): load, so iframes such as reCAPTCHA or maps keep working. They cannot reach the bridge because the badge is main-frame only and their origin is not trusted.
  3. `about:blank`, `blob:`, `file:`, `javascript:`, `data:` in the top frame: block.
  4. Any other URL (other `http(s)` hosts, `tel:`, `mailto:`, `sms:`, `whatsapp:`, …): `Linking.openURL(url)` and block.
- `originWhitelist` is left to the consumer. Its default is `['http://*', 'https://*']` so that `localhost` works in development.

## 7. Behaviors that must be covered by automated tests

Logic lives in pure functions, which keeps it testable with `bun test` and no React Native runtime. `BridgeWebView` is a thin wrapper that only wires these functions to props.

**Web client (`/web`)**, using a fake `window`:

1. `isApp` is false without the badge, and true with the badge and `ReactNativeWebView` both present.
2. Importing the module with no `window` (SSR) does not throw.
3. `call()` outside the app rejects with `NOT_IN_APP` and does not post.
4. A `res` with a matching `id` resolves or rejects the right promise. A `res` with an unknown `id` is ignored.
5. `call()` rejects with `TIMEOUT` after `timeout`. A late response after the timeout is ignored.
6. `on()` receives `evt` payloads, and unsubscribing stops delivery.
7. Non-bridge `CustomEvent`s and malformed payloads are ignored.

**Native core**, as pure functions:

8. Message routing:
   - a bridge request from a trusted host calls the handler and produces a `res`;
   - an unknown method produces `UNKNOWN_METHOD`;
   - a handler that throws produces its own `code`, or `HANDLER_ERROR`;
   - an untrusted host produces nothing.
9. Non-bridge messages are forwarded to the consumer `onMessage`, and so is invalid JSON.
10. Host matching: exact, wildcard, and look-alike rejection (`evilbrand.com`, `brand.com.evil.io`).
11. Navigation policy: every case in §6, including `inAppHosts`, plus consumer override precedence (`true`, `false`, `undefined`). Message routing drops requests from an `inAppHosts` origin.
12. Injected script composition: badge first, then consumer script, and the result is valid JS.
13. Emitter queue: events emitted before load are delivered in order after load. Nothing is lost or duplicated across a reload.
14. The JS built for `injectJavaScript` safely embeds arbitrary JSON (quotes, `</script>`, U+2028/U+2029).

## 8. Example app and end-to-end verification

### 8.1 `example/`

- `example/app/`: an Expo SDK 57 (the current SDK; the one Expo Go supports) app that runs in **Expo Go** (no native build). It has a single `BridgeWebView` pointing at the example web page, with these handlers:
  - `camera.requestPermission` (expo-camera, with the "open settings" fallback)
  - `haptics.impact` (expo-haptics)
  - `app.unsupported` (native `Alert`)
  - `test.echo`
  - `test.sleep` (to exercise timeouts)
  - `test.throw` (throws `{ code: 'CUSTOM' }`)

  It emits `app.stateChange` from `AppState`, and emits a `test.early` event on mount, before the page loads. It also has a consumer `onMessage` that shows legacy messages in a native banner.
- `example/web/`: a static page served locally, importing the built `/web` bundle. It has one button per scenario and a log panel that shows each result or error.

### 8.2 Scenarios verified on the iOS simulator and the Android emulator

Claude runs these end to end with the simulator tooling, taps each button and checks the result.

1. The badge is visible: `isApp`, platform and version are shown on the page.
2. `test.echo` round-trips params.
3. `camera.requestPermission` shows the iOS permission dialog and resolves `{ granted }`. The simulator has no real camera, so only the permission flow is checked.
4. `haptics.impact` resolves. The simulator does not vibrate, so resolution is the check.
5. `app.unsupported` shows the native alert.
6. `nope.nothing` rejects with `UNKNOWN_METHOD`, and `test.throw` rejects with `CUSTOM`.
7. `test.sleep` with a short timeout rejects with `TIMEOUT`.
8. The `test.early` event emitted before load is shown on the page after load.
9. Backgrounding and foregrounding the app delivers `app.stateChange`.
10. A link to an external host opens Safari. A link to the same host stays in the app.
11. A legacy `{ event_name }` message reaches the consumer `onMessage` banner.
12. An iframe served from an untrusted host (`127.0.0.1` when `localhost` is trusted) cannot get a response. **Open question to settle here:** it is unverified whether `react-native-webview` reports the iframe's URL or the top frame's URL in `nativeEvent.url` for subframe `postMessage`s. If it is the top frame's, the origin check alone does not stop an iframe. In that case the limitation is documented in the README, and "do not embed untrusted iframes on bridge-enabled pages" becomes an explicit rule.
13. The same page opened in Safari (outside the app) shows `isApp: false`, and calls reject with `NOT_IN_APP`.
14. The page loads Google Analytics (`gtag.js`) and third-party iframes (a map embed and a GTM `ns.html` iframe). Neither the app nor the page is sent to the browser, and the map renders.
15. A link to an `inAppHosts` host (`127.0.0.1` in the example) opens inside the app.
16. A bridge call made from that `inAppHosts` page rejects with `TIMEOUT`, because the native side drops it.

The same scenarios also run on the Android emulator (driven with `adb`, using `adb reverse` so that `localhost` resolves to the Mac). The exceptions are scenario 3's dialog wording and scenario 13, which uses Chrome instead of Safari. Android does not report `isTopFrame`, so scenario 14 is where platform differences in the iframe policy would show up.

## 9. Release

- **First publish:** the repo and npm package don't exist yet. Creating the GitHub repo, pushing, doing the first `npm publish` and configuring the npm trusted publisher are outward-facing steps. Claude asks before each one. The npm login and first publish are done by the user.
